# ADR-0001：声纹候选的采样来源与策略

- 状态：已接受
- 日期：2026-07-31
- 影响范围：`core/voiceprint_sampler.py`、`core/speaker_linker.py`、`services/indexing.py`、`config.py`

## 背景

跨录音说话人合并（`SpeakerLinker`，M7 架构 §8）以"每条录音、每个说话人一个 192 维声纹向量"为输入。这个向量从哪段音频提取，此前从未被裁决过：

- 唯一的说法是 `core/speaker_linker.py` 模块 docstring 里的一行 "Build candidate voiceprint from the longest segment"，既没有实现，也没有测试锁定，PRD 的 L1–L10 / Q1–Q4 与各版 QA 报告均未涉及。
- `SpeakerLinker.run()` 的文档把候选组装的责任交给调用方（"Caller is responsible for assembling these"），而这个调用方在 M7–M9 从未落地：生产代码中 `_NewSpeakerCandidate` 零构造、`extract_voiceprint` 只被 eval 评测调用、`services/indexing.py` 构造 `Chunker` 时没有传 `enable_voiceprint`，因此连 diarization 都没跑，`Segment.speaker` 恒为 `None`。

结论是整条声纹采集链路当时处于断链状态。同时存在一个具体的误用风险：接待（reception）功能会用 `AudioAssembler` 把多条录音拼成一个物理合并音频（`Reception.merged_audio_path`），这个产物容易被误当作声纹提取的输入。

## 决策

### 一、合并接待音频不得作为声纹提取的输入

`merged_audio_path` 是**多说话人混合时间轴**。CAM++ 的说话人向量是对全部帧做统计池化后得到的，混入多人语音后，结果向量落在多个说话人子空间的凸组合上——它不代表其中任何一个人，却会以中等余弦同时"像"多个真实说话人，从而在 Layer-1 阈值下造成系统性错误合并。

合并产物还叠加了三重不可逆的信息损失（见 `core/audio_assembler.py`）：

- 强制单声道降混，双信道电话录音的坐席/客户分离信息被销毁；
- 全部源重采样到 16 kHz，AAC 目标额外经过 96k 有损再编码；
- 段间用 `adelay` 插入纯数字静音，稀释统计池化的有效帧占比。

因此声纹采样一律读取录音自身的原始音频（`Recording.path`）。`VoiceprintSampler` 的模块 docstring 与 `_stage_speaker_link` 的注释都写明了这一点，并有测试 `test_samples_the_recordings_own_audio` 锁定。

### 二、采样策略默认为逐段加权均值（`weighted_mean`）

对同一说话人的每个合格 diarization 片段各提取一次 embedding，按片段时长加权平均后重新 L2 归一化。

与另外两个候选方案的对比：

| 方案 | 准确性 | 对 diarization 错误的鲁棒性 | 成本 |
|---|---|---|---|
| 逐段加权均值（采纳） | 好 | **好**：错分片段只占 1/N 权重，且可被离群剔除 | N 次提取，总音频时长与拼接相同 |
| 按说话人拼接后提取一次 | 好 | 差：错分片段的帧直接进入池化，事后无法剔除 | 1 次提取，但需新增多区间端点或客户端拼接 |
| 最长片段单次提取 | 差~中：客服场景客户常只有短句，最长片段可能不足 3 秒 | 差：单点故障，最长片段若归属错误则整个声纹全错 | 最省 |

拼接方案相对加权均值没有准确性优势，鲁棒性和实现复杂度反而更差，不予采纳。最长片段方案保留为 `longest_segment` 配置项，用于成本敏感场景或与历史行为对比，但不是默认值。

离群剔除：先算一次质心，丢弃与质心余弦低于 `voiceprint_sample_outlier_cosine`（默认 0.5）的片段后重算。样本少于 3 个时不启用——没有多数可供判断，丢掉一个只会让证据减半。

判定归属用的是**等权**质心（一段一票），只有最终模板才按时长加权。若用加权质心做判定，最长的片段会主导它自己被检验的那个平均值，一个错分的长片段就能"自证清白"——这恰恰是最需要被剔除的情形。

### 三、质量门控

| 配置项 | 默认值 | 作用 |
|---|---|---|
| `voiceprint_sample_min_segment_sec` | 1.0 | 更短的片段不参与提取：亚秒级 embedding 被噪声主导，会把同人余弦压到 Layer-1 阈值以下 |
| `voiceprint_sample_min_total_sec` | 3.0 | 合格语音不足此值的说话人**不建立**跨录音声纹，而不是建立一个不可靠的 |
| `voiceprint_sample_max_segments` | 8 | 每人每录音的提取次数上限，取最长的若干段 |

跳过的说话人会记入 `SpeakerSampleReport.skipped_speakers` 并附原因，而非静默丢弃。

注意这里有两个容易混淆的时长，必须分开：

- `SpeakerNode.total_speech_sec` 统计该说话人的**全部**语音，包括短到无法采样的片段——它描述这个人说了多少话。
- `VoiceprintVector.duration_sec` 只统计**真正产生了这个向量**的音频（扣除提取失败与离群剔除的部分）——它描述这条向量有多可信，代表模板的排序用的就是它。

两者混用会让"最长样本胜出"名不副实：一个有 200 秒零碎应答但只有 3 秒可用语音的说话人，会凭总时长压过一段 120 秒的独白。

采样来源的另一个约束：裁剪窗口必须取自 **diarization 时间轴**，而不是 VAD 分段。VAD 按静音切分，一个 VAD 段可能横跨换手（对话中 300 毫秒以内的换手静音通常被合并），却只携带其中点所属者的标签；再叠加"最长优先"的选样，等于系统性地挑中污染最重的窗口。这与本 ADR 第一节反对合并接待音频是同一个失败模式，只是尺度更小、更隐蔽。为此 `ChunkerOutput` 保留了 `diarization` 时间轴，`_stage_speaker_link` 优先使用它，仅在没有时间轴时回退到带标签的 VAD 段。

### 四、代表声纹改为"最长样本"而非"最新样本"

`SpeakerLinker._load_existing_speakers` 原先按 `created_at DESC` 取每个说话人的最新一条向量作为比对模板。这意味着一次余弦 0.5 边缘的 AMBIGUOUS 合并所写入的低质量向量，会成为该说话人此后唯一的代表声纹，并持续拖累所有后续匹配（模板漂移）。

改为按 `duration_sec DESC` 优先，`created_at DESC, id DESC` 兜底。embedding 质量随语音时长上升，最长的样本是最可信的模板。所有向量行仍然全部保留，审计与 DSAR 链路不受影响——变的只是"选哪一条当模板"。

对应索引 `ix_vp_tenant_speaker_duration` 由迁移 `0032_voiceprint_duration_index` 建立。需要说明它的作用边界：它只能缩小按租户读取的行数，**并不能消除排序**——这个排名用的窗口函数位于派生表中，MySQL 8 一定会把派生表物化，而 ORDER BY 又混合了升序的分区键与降序的排序键（还包含不在索引里的 `created_at`、`id`），因此租户内仍会发生一次 filesort。`_load_existing_speakers` 本身就是全租户加载的设计，这个开销是该设计固有的，不是索引能解决的。若将来这里成为瓶颈，正确的方向是改成按需查询单个 speaker，而不是继续加索引。

## 后果

**正面**：声纹链路从断链变为可运行（`enable_voiceprint=True` 即生效）；单个 diarization 错误不再能污染整个候选；短促发言不再产生不可靠的跨录音身份；低质量样本不再能劫持说话人模板。

**代价**：每个说话人的提取次数从 1 次上升到最多 8 次。CAM++ 推理开销近似与音频总时长线性相关，而两种策略处理的总时长相同，因此增加的主要是 HTTP 往返次数，不是推理算力。

**默认开启**：链路端到端打通并经三轮对抗评审后，`enable_voiceprint` 默认值改为 `True`。开关本身不足以让它运行：`_stage_speaker_link` 要求特性开关、CAM++ adapter、settings、加密密钥四者齐备——缺任一项的部署保持关闭，而不是写出未加密或无法关联的声纹。设为 `False` 可精确恢复 M3–M6 行为（不做 diarization，`Segment.speaker` 恒为 `None`）。

对既有租户，翻转默认值**只影响此后入库的录音**；存量数据仍需跑一次 `scripts/backfill_voiceprints.py`。

该阶段整体为 best-effort：声纹服务故障只记录告警，不会让一次本已完成的索引失败（但 `CancelledError` 例外，进程退出不能被当成链接失败吞掉）。

**重跑与并发**：索引流水线是可重试的（任何一次瞬时失败都会重跑整条），而声纹链接**不是幂等的**——采样对同一录音是确定性的，第二次会产出同一个 `voiceprint_id` 并撞上唯一索引，异常会中断候选循环；而已经成功的合并则会把说话人时长重复累加。因此该阶段在采样**之前**先检查，有则跳过（顺带省掉重试时的全部提取开销）；`_persist_voiceprint` 另有一层重复检测。

这个幂等守卫的粒度必须是**候选**而不是录音，而且三个入口的**前置**检查也必须同样是候选级——否则那道"省成本"的早退会把半链接的录音直接挡在续传逻辑之外，等于白修。索引路径手上就有 diarization 时间轴，可以直接比较"这条录音有哪些说话人"与"哪些已链接"；流式路径没有时间轴可比，索性不做前置检查，交给锁内的权威判断（它现在是后台任务，diarization 的开销不在关键路径上）。每个候选各自提交（向量、节点聚合、链接三次独立事务），所以一次中途失败会留下"spk_0 已链接、spk_1 没有"的状态；若守卫只问"这条录音有没有任何链接"，它此后会被三个入口一致判定为已完成，spk_1 永远丢失且只留一条 warning。`linked_speaker_labels()` 按 `source_speaker_label` 返回已完成的标签集合，链接前据此过滤候选，于是下一次运行能把上次没做完的部分补上。（`recording_is_linked()` 保留给迁移 0035 之前、标签无法还原的旧数据。）

跨 worker 并发方面，链接是"读快照—判断—写入"跨多个事务的过程，两个 worker 同时处理同一个人的不同录音会各建一个 SpeakerNode，而目前没有任何离线合并作业。因此链接段用租户级 MySQL 咨询锁串行化（`core/tenant_lock.py`）；耗时的采样留在锁外。拿不到锁时降级为不串行执行——重复节点可被人工复核，而丢失链接不可恢复。

这里有个不直观的陷阱值得记下：MySQL 的 `GET_LOCK` 绑定的是**连接**，而 SQLAlchemy 会把连接归还连接池。实测确认，若 session 在未释放锁的情况下关闭，这条连接会**带着锁**回到池中（`IS_FREE_LOCK` 返回 0），下一个借用者直接继承它，而其他连接上的 worker 会一直阻塞到该连接恰好被回收。因此释放失败时（包括任务被取消、`RELEASE_LOCK` 本身执行不了的情况）必须 `invalidate()` 掉这条连接——关闭连接才是让 MySQL 真正释放锁的手段。`tests/core/test_tenant_lock.py` 锁定了正常、抛异常、被取消三条路径的释放行为。

**存量数据**：打开开关只影响此后入库的录音。此前的录音是在 diarization 关闭的状态下切分的，段上没有说话人标签，永远不会自己长出跨录音身份——而这恰恰是既有租户最需要的部分。`core/voiceprint_backfill.py` 负责补齐：它不能复用 `ChunkerOutput`（那些录音从未被 diarize 过），因此对存储的音频重跑 diarization，再按同一套采样与链接逻辑处理。入口是 `scripts/backfill_voiceprints.py`，按 `--limit` 分批、可重复运行，并与在线管线共用同一把租户锁。

分批推进靠的是**录音 ID 游标**，不能只靠"还没有链接"来筛选：有相当一部分录音永远不会产生链接——音频被保留期清理了、diarization 找不到语音、没有说话人过得了质量门——它们会把每一批都填满，后面的录音永远轮不到。脚本自动按游标连跑多批（`--max-batches` 兜底），`BackfillReport.last_scanned_id` 是可传回的续跑位置。

`SpeakerLinker.link_speakers()` 曾是这件事的占位实现——一个返回空列表的空壳，docstring 却声称有 nightly cron 调用、已接入 scheduler，两者都不属实。它现在抛 `NotImplementedError` 并指向回填作业：空壳返回 `[]` 与"确实无事可做"无法区分，是比报错更坏的失败方式。

## 流式路径

流式会话**不做**逐 chunk 的说话人链接。说话人身份是由这个人的全部语音决定的，而 `DeltaGraphUpdater.update()` 每个 chunk 调用一次——挂在那里会对同一批人反复链接。它也无法复用 diarization 时间轴：流式从不跑批量 diarization，其 PCM 帧只是临时暂存，Segment 落库后即被丢弃。

因此流式在**会话收尾时链接一次**（`api/ws_stream.py`），走与回填相同的 `core/recording_speaker_link.py`：重读该会话所绑定录音的音频，再采样、链接。若该录音没有可读音频（纯流式采集），记录原因后照常关闭会话——一次已经结束的会话不该因为解析不出说话人身份而失败。

这项工作必须**脱离会话协程**执行，且排在最后。它要重读整条录音（一次 diarization 加每个说话人最多 8 次提取，每次都是整文件上传），而流式 ASR 连接是每租户信号量池化的：如果在 finally 里 `await`，这个已经逻辑结束的会话会一直占着池许可，同租户连续 8 个会话结束后，第 9 个新会话会被直接以 1011 拒绝——一个可自我复现的服务级拒绝。同时 `session_closed` 帧与 socket 关闭也会被拖同样久。因此改为在归还池许可、发完收尾帧、关闭连接之后再派发后台任务，并登记到 `app.state.speaker_link_tasks`，让进程关闭时**等待**而不是取消它们（每个链接是若干次独立提交，中途杀掉会留下半链接的录音）。

`DeltaGraphUpdater` 的 `speaker_links` 字段保留为 0 并保持报告结构不变，其 `linker_factory` 参数同理只为调用点兼容而保留、从不被调用；两处都已在注释中写明原因，不再声称"deferred to round 2"。

## 局部标签到说话人的映射

Segment 只保存 diarization 的局部标签（`spk_0`），而 `speaker_links` 此前只记录规范节点 ID，两者之间没有桥梁——因此任何按段展示说话人的界面都只能显示 `spk_0`，既说不出是谁，也说不出这个归属有多可靠。

`speaker_links.source_speaker_label`（迁移 `0035`）补上了这一列，`GET /recordings/{id}/speakers` 把它暴露为"标签 → 说话人 + 质量标记"的映射。该列可空：迁移之前写入的链接无法还原其标签，而猜测会把话安到错的人头上，所以这些行直接不返回。

接待工作台的时间轴消费这个映射：能解析出来就显示真实姓名与角色，`AMBIGUOUS` 的加 ⚠ 前缀；解析不出来（声纹链路未启用或未跑过）就保留原始标签——凭空造一个身份比显示 `spk_0` 更糟。

## 读权限

`GET /speakers` 与 `GET /speakers/{id}` 从 inspector+ 放开到 **viewer+**。

原先的分界是无意造成的：复核队列（`/speakers/merge-pending`）和策略端点一直是 viewer+，而说话人清单是 inspector+，结果 viewer 能看到"某条合并被判定为存疑"，却看不到这条合并所指的说话人是谁——一个只能看见结论、看不见对象的视图。

放开是安全的：这两个端点不返回任何生物特征数据，只返回 §17.1 规定的截断声纹哈希（本身就是指纹而非原始向量）、角色与合并元数据，而截断哈希本来就已经通过复核队列暴露给 viewer 了。租户隔离不变，**写操作（确认/驳回合并）仍是 inspector+**。

## 命名修正

`RecordingCandidate.customer_voiceprint_id` 已更名为 `customer_hash_claim`。它存的是 ingest 时调用方自报的 `Recording.customer_hash`，与 CAM++ 声纹毫无关系；旧名字读起来像是声纹管线的产物，会诱导把一个未经验证的客户端声明当成生物特征匹配来用。它是纯内存字段（从来不是数据库列），因此改名不涉及迁移。

## 阈值校准

Layer-1 阈值 0.5 / 0.7 本就是普通配置项，改起来不难；难的是知道该改成多少——它们从未用自有数据校准过。`config.py` 注释称 0.5 是"CAM++ 论文推荐"，但 ModelScope 官方 SV pipeline 的默认判定阈值约为 0.3，出处存疑。阈值的合理性还与采样策略强耦合：加权均值的分数分布比单短片段更靠上、方差更小。

`scripts/calibrate_voiceprint_thresholds.py` 把这件事变成可执行操作：给一批标注试验对，它用当前配置的 adapter 提取声纹、统计同人/异人余弦分布，并给出两个阈值的建议值（`AMBIGUOUS` 取目标误接受率处，`COSINE` 取等错误率点）。它只打印建议、不改配置。mock 模式可完整验证这条工作流本身。

有三处约束是必须的，否则"建议值"会是用户无法采纳的：

- **两个阈值不能倒置**。配置校验要求 `COSINE ≤ AMBIGUOUS`，而数据分得好时误接受率目标恰恰在等错误率点**之下**就已满足，天然会产出倒置的一对。此时把合并下限钳到较严的那个值并说明原因，而不是打印一对会让服务拒绝启动的数字。
- **不能给出半套建议**。等错误率点无解时，只采纳 `AMBIGUOUS` 会让它与既有的合并下限配对，同样可能被判定为倒置。因此两者要么都给，要么都不给。
- **FAR 阈值必须在全分辨率上算**。`EERResult.roc_curve` 为了出报表被下采样到 101 个点，若在这条粗化曲线上扫描，几千对的试验集里每几十个候选阈值才看一个，返回值会系统性偏严，而且与并排打印的等错误率阈值不是同一分辨率。`EERResult.threshold_at_far()` 用的是完整扫描结果，并排除了 ±inf 哨兵——上界哨兵的误接受率恒为 0 只是因为它什么都不接受，那是算术，不是阈值。

试验对文件由 `scripts/build_voiceprint_trials.py` 生成，支持两种布局：一个说话人一个目录（CN-Celeb 的 `data/` 树，也适合自建标注集），或 CN-Celeb 官方评测列表（结果可与公开数字对比）。语料分工在 `docs/DESIGN.md` §8 已裁决：**声纹 EER 用 CN-Celeb，AliMeeting 是 DER 基准**。

`tests/core/test_calibration_round_trip.py` 把"生成试验对 → 校准 → 写进配置 → 链接"当成一个闭环来验证，因为这才是运维实际执行的流程：单个环节各自正确、而闭环断掉，产出的会是一个看起来合理却把不同人链在一起的阈值，任何单组件测试都发现不了。它验证四件事——推荐值确实能被 `Settings` 接受（不越界、不倒置）；这对阈值用回它自己的语料时，同人对全部达到无歧义合并、异人对全部够不到合并下限；语料本身不可分时工具拒绝给建议而不是编一个数字；以及生成器写出的每一行解析器都读得回来。

真正剩下的是准备一批有代表性的标注音频——那是数据工作，不是工程工作。

mock 模式下有个刻意的限制：说话人验证打分**不能**传 `speaker_id`（身份正是被测量的东西），而 mock 听不见任何声音，所以默认每个文件各算一个说话人，EER 恒为 0.5——工具会如实报告"无等错误率点"，而不是编一个数字。`--mock-speaker-from-filename` 可以让它按文件名词干猜身份（`alice_01.wav` 与 `alice_02.wav` 算同一人），从而完整验证这条工作流；这是显式开关而非默认值，因为生产文件名多是时间戳或 UUID，`20260801_1030.wav` 和 `20260801_1045.wav` 会被静默判成同一个人。开启时输出会标明"身份取自文件名而非音频"。
