1. 总体架构 Overall Architecture

两层架构：流水线状态层（MySQL） + RAG 引擎层（文件索引），由 recording_id 桥接
关键洞察：VideoRAG 喂给知识图谱的文本本来就是 ASR 转写（transcript）。砍掉视觉附属（MiniCPM-V + ImageBind），整个图谱 RAG 内核对音频完全成立，且 transcript 信息密度高于稀疏抽帧 caption，图谱质量更优。

3. 存储分层 Storage Layers

VideoRAG 文件索引（复用）+ MySQL 状态层（新增）+ BaseStorage 抽象让三类存储可插拔

Phase 1 决策：全 MySQL 暴力余弦

KV（kv_store_*.json）→ MySQL
✅ 容易且推荐。就是字典行存即可，比 JSON 文件好（可查/并发/统一备份）
向量库（vdb_*）→ MySQL 暴力
⚠️ 看规模。小规模（<10万）暴力 MySQL ≈ NanoVectorDB 无损；大规模需 ANN
图库（graphml）→ 保留 NetworkX
❌ MySQL 不建议。图遍历在关系库痛苦；要上 DB 用 Neo4j（BaseStorage 已支持）

4. 标签版本化与增量重算 Tag Versioning & Incremental Recompute

版本是地基 · diff 驱动最小重算 · LLM 缓存驱动的幂等重打
关键精度：要版本化的不是"标签值"，而是"判定本身"——一条 version 行须带上产生它的配方： (recording_id, tag_path, tag_value, prompt_version, model_version, source, input_hash, computed_at, confidence)

9. 设计原则 Design Principles

复用优先 · Reuse First
图谱内核、存储抽象、检索-重排逻辑原样继承自 VideoRAG，零改动
模态替换 · Modality Swap
视觉预处理整体替换为音频预处理（VAD + ASR），不改造内核
两层分离 · Two-Layer Separation
MySQL 管流水线状态/版本/审计，VideoRAG 文件索引管 RAG 检索，各司其职
治理前置 · Governance First
标签版本化 + 增量重算 + LLM 缓存幂等重打，从设计期就内建
评估驱动 · Evaluation Driven
分层评估框架（A0/A1/A2/B），prompt 改动有量化指标，不靠感觉
借鉴开源 · Stand on Giants
工程产物形态借鉴 Graphify（三件套 + 边置信度）；检索范式借鉴 GraphRAG（社区/分层/DRIFT）
